# Support Triage & Resolution Agent

The submission intentionally prioritizes the architecture around AI classification and drafting—not model sophistication. The existing support case system remains the source of truth and manual safety net; this service adds triage, category policy, structural safety gates, sanitized routing, auditability, and a modeled human approval/release boundary.

## Run

```bash
go test ./...
go vet ./...
go run ./cmd/server
```

Example triage request:

```bash
curl -X POST http://localhost:8080/v1/triage \
  -H 'Content-Type: application/json' \
  -d '{"id":"case-1","member_id":"member-1","text":"How do I update my profile?"}'
```

## What the prototype demonstrates

- one shared triage pipeline for General Q&A, Product Feedback, and Compliance;
- configuration-driven category policy and category-specific confidence thresholds;
- an independent safety assessment that can override an incorrect classifier;
- a final egress invariant check before an action can progress;
- fail-closed degraded behavior for low confidence and dependency failures;
- sanitized/allowlisted cross-team routing context;
- pre-side-effect audit persistence for automated routing;
- an explicit human approval/release gate for member-facing drafts, authorized from authoritative audit state rather than caller-supplied data;
- audit updates that record who approved a response and when, using a server-generated timestamp and a single atomic transition out of `pending`;
- classifier confidence and reason codes normalized at the trust boundary before any policy lookup;
- a Compliance no-draft invariant enforced by the effective category itself, independent of safety flags and policy configuration;
- CI tests that intentionally pressure-test compliance, classifier, and sensitive-data invariants.

`POST /v1/triage` is synchronous only to make the exercise easy to run and review. The RFC proposes queue-backed asynchronous triage for production bursts.

The prototype does **not** implement a new member-send mechanism. `Service.ReleaseForMember` models the final approval boundary and returns a releasable payload only after a valid human approval has been durably audited; the existing member-send workflow remains deliberately outside this service.

## Trust boundaries

Each boundary below is enforced in code and covered by a permanent test.

**Member release.** `ReleaseForMember(ctx, decisionID, approval)` takes a decision ID, not a caller-supplied `Decision`. Eligibility is read from authoritative audit state, so a caller cannot assert its own category, action, or approval status. The audit stores the SHA-256 of the original generated draft and never the raw draft text. An unchanged approval must supply a reviewed response whose hash matches that stored hash exactly, so a mutated draft cannot be released as "approved unchanged". An edited approval is re-inspected through the same safety detector and fails closed. Approval is applied as one atomic compare-and-set from `pending`, which rejects replayed and stale approvals, and the approval timestamp is generated by the service rather than accepted from the request. `ReviewerID` is a prototype assumption: reviewer identity is taken as already authenticated by the upstream care workflow, and this service does not implement authentication or authorization.

**Sensitive data.** One shared detector/redactor backs both safety assessment and routing-summary sanitization, so detection and redaction cannot drift apart. It covers formatted SSNs, email addresses, card-like digit sequences, `acct_`/`account-` style tokens, values explicitly labeled as an account or routing number (including space- and hyphen-separated groups), and long contiguous digit runs. The words "account" and "routing" are not sensitive on their own, so ordinary member wording still routes normally. The same boundary inspects generated drafts before a draft is attached to a decision or audited, and inspects edited responses at release.

**Routing metadata.** Metadata is allowlisted by key *and* validated by value: `channel` against a closed set, `locale` against a locale shape, and `app_version` against a bounded semantic-version shape. An invalid or sensitive value is omitted rather than copied or echoed back.

**Classifier output.** Confidence must be finite and within `[0,1]`; `NaN`, both infinities, and out-of-range values escalate to a human before any threshold comparison or policy lookup. Reason codes are accepted only from a closed, code-owned set matched to the classified category, so arbitrary model or provider text never reaches a decision, a routing context, or an audit record. Invalid classifier output degrades to the human path under service-owned reason codes.

**Compliance.** An effective category of Compliance forbids a member draft on its own. The rule is checked before drafting executes and again during final decision validation, independent of safety flags and of mutable policy configuration, so a malformed policy registry that appears to permit Compliance drafting still produces no draft and never invokes the drafter.

## Prototype limitations

Sensitive-data detection is deterministic and regex-based. It is deliberately bounded protection for reviewed patterns at a demonstrated trust boundary, not a production DLP or entity-recognition system; new sensitive formats belong in the shared matcher with a focused test. Authentication and authorization, durable transactional storage, provider adapters, queueing, and the member-send integration remain out of scope and are discussed in `RFC.md`.
